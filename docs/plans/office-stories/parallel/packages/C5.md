## Результат и API

Предлагаемые функции верхнего уровня: createDaily, startDaily, tickDaily, enterDaily, leaveDaily, setDailyMode, answerDaily.
До начала проверить отсутствие конфликтующего объявления в своей базе. Уже согласованные имена не переименовывать молча.
Поздний пакет, draft до принятия основной волны. Модель не стартует игру и не заменяет старый standup сама. Передаются clockMinutes,dt,attendance,legalAway,questionAt,availableSirgey,paused. questionAt адаптер выбирает через rand один раз. Учитывать 80% из 22.5с, часы и dt не смешивать. Ответ/рилсы/следующая задача по29, вопрос с сохранённым deadlineRemaining. Особо: при общем вызове tick не начислить обычный Excel; это обязательство адаптера. Все выплаты и наказания только как однократные outcome descriptors.

1. Прочитать исходные карточки и фактический код, указанный там; не реализовывать их адаптерные правки.
2. Описать в handoff минимальный JSON state и обязательные context-поля.
3. Реализовать функции без globals DOM/store/player/boss и без верхнеуровневых побочных эффектов.
4. Использовать единый результат из API.md, если вызов меняет состояние. Для чистых запросов допустим boolean/DTO согласно описанному контракту.
5. Добавить тесты наблюдаемого результата и JSON round trip; отрицательные/неполные context проверяются безопасным отказом.
6. Запустить адресный тест, синтаксис и проектный QA по COMMON.md. Не включать модуль в index ради теста.
7. Сделать отдельный commit пакета, указать фактические сигнатуры и примеры входа/выхода. Продолжить следующий пакет своего блока без дополнительного подтверждения.
